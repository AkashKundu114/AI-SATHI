# Engineering Review Checklist

Use this file for a enterprise-grade code and systems review. It names the core
invariants, what is covered by tests, and what a reviewer should inspect first.

> **Deployment target for this checklist:** the Azure low-cost pilot
> (100 users, ~2,000 msgs/day) described in `docs/architecture.md` §11 and
> `README-azure-deploy.md`. Where an item below differs from what the
> codebase would look like at the PRD's 12-month target scale
> (`docs/product.md` §4.2), that's noted inline - this document reviews
> the system that's actually deployed, not the long-term vision.

## High-Level Claims

- Valid Meta webhooks are acknowledged quickly and processed asynchronously
  (in-process via `BackgroundTasks`, not a separate queue - see below).
- Duplicate WhatsApp retries do not create duplicate ledger writes
  (enforced in Postgres now, not Redis).
- User-visible financial numbers are computed by code, not generated by an LLM.
- Model/vendor failure degrades to bounded Bengali retry messages.
- Market advice cannot expose trends from fewer than the minimum seller sample.
- The active deployment path is a **single Azure Container App** + managed
  Postgres + Azure Blob Storage (Bicep in `infra/`) - not Docker Compose on
  a single host, and not the original four-service (gateway + worker +
  Redis + MinIO) shape.

## Test Expectations

Run:

```bash
pytest tests/unit/ -q --tb=short
pytest tests/integration/ -q --tb=short
```

The unit and integration suites are offline and should not require API keys.
Fixtures live under `tests/fixtures/`; keep them small, synthetic, and free of
real user data.

Unit coverage includes:

- Webhook signature behavior.
- Bengali number helpers and calendar formatting.
- Ledger amount validation and confirmation flow.
- Pricing floor math.
- Negotiation floor and number-safety behavior.
- Catalog delivery fallbacks.
- Flux fallback behavior.
- Market trend classification.
- Grounding verifier behavior for scheme RAG components.
- Graph routing.

Integration coverage includes:

- Meta webhook HMAC verification, Postgres-based dedup, and in-process
  dispatch. *(Previously: Redis dedup + Celery queue handoff - the
  fixtures in `tests/integration/test_webhook_gateway.py` mock
  `get_redis`/`_dispatch_to_orchestrator`; these need updating to mock
  `shared.db.dedup` and `services.gateway.turn_processor` instead before
  this suite is green against the current `main.py` - flagged as a known
  gap, not silently assumed fixed.)*
- WhatsApp webhook fixture parsing for text, audio, image, and interactive
  payload shapes.
- Gateway audio/image dispatch into STT, Blob Storage upload, and
  in-process turn queueing. *(`tests/integration/test_gateway_dispatch.py`'s
  `get_s3_client` mock needs the same update - see
  `tests/unit/test_catalog_node.py`'s `_FakeS3` fixture, called out in
  `README-azure-deploy.md` as a known follow-up.)*
- Orchestrator outbound delivery for text, document, and image messages.

**Known test-suite gap as of this pass:** the storage- and
queue-facing fixtures across `tests/unit/test_catalog_node.py`,
`tests/integration/test_gateway_dispatch.py`, and
`tests/integration/test_webhook_gateway.py` still reference the removed
`boto3`/Redis-shaped mocks. This is a **test-authoring debt, not a
production bug** - the application code itself no longer imports either
removed module - but it means `pytest` will not be fully green until those
fixtures are updated to mock `blob_client`/`dedup` instead. Treat this as a
blocking item before signing off "tests pass," not an optional cleanup.

## Production Readiness Bar

Before live users:

- No stale references to Redis, Celery, MinIO, or boto3 in active docs or
  code (`grep -rn "celery\|redis\|boto3\|minio" --include="*.py" services/ shared/`
  should return nothing outside the two deprecation stubs).
- `make check-env` passes, updated for the current required variable set
  (`DATABASE_URL`, `AZURE_STORAGE_CONNECTION_STRING`, `SARVAM_API_KEY`, WA_*
  - no `REDIS_URL` anymore; confirm `scripts/check_env.py` has been updated
  to match `shared/config/settings.py`'s current required fields).
- Unit tests pass - see the known gap above before treating this as
  unconditionally true.
- Meta Business Verification and permanent token are complete.
- Sarvam spend cap is set.
- Postgres Flexible Server password is non-default; firewall rule is
  scoped as narrowly as your Azure networking setup allows (the default
  Bicep uses the "allow all Azure services" convenience rule - tighten
  this with a VNet/private endpoint before this holds data you can't
  afford to leak, per `infra/modules/postgres.bicep`'s own comment).
- Storage Account container access is `None` (no public blob access) -
  reads only via time-limited SAS, confirmed in `infra/modules/storage.bicep`.
- `webhook_dedup` / `rate_limit_counters` have a retention-cleanup plan
  before this has been running unattended for more than a few months (see
  `docs/red-team.md` §11.1 - flagged, not yet automated).
- Incident owner knows how to inspect the single Container App's logs via
  Log Analytics (`az containerapp logs show` or the Azure Portal - there
  is only one app to check now, not a gateway/worker pair).

## Known Review Risks

- Government Scheme RAG is not part of active production routing.
- **Single Container App replica, no queue.** This is the biggest
  structural difference from a traditional "designed for scale" review:
  there is no horizontal redundancy and no backpressure mechanism. This is
  an explicit, cost-driven choice for a 100-user pilot
  (`docs/architecture.md` §11.6) - a reviewer coming from a
  higher-scale background should not treat this as an oversight to flag
  and fix, but should confirm the scale-up triggers in
  `docs/product.md` §10.5 are actually being watched.
- **No local model fallback provisioned.** A sustained Sarvam outage takes
  every text/voice/vision agent down to a friendly-error mode for its
  duration - a real, accepted vendor-dependency risk at this scale (see
  `docs/security.md` §7.5).
- Postgres now carries two additional jobs (dedup, rate-limiting) it
  didn't have before, on the same connection pool as the LangGraph
  checkpointer and every domain table - watch Postgres CPU/connection
  metrics specifically as a leading indicator of outgrowing this tier
  (`docs/red-team.md` §11.1).
- External vendor APIs (Sarvam, Flux Pro, Meta) can change. Pin behavior
  with integration tests before scaling beyond pilot traffic.
- Test-suite fixtures lag the storage/dedup migration (see "Known
  test-suite gap" above) - do not sign off on "green tests" without
  checking this first.
